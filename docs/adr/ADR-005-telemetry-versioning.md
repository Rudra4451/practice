# ADR-005: Telemetry Payload Versioning Protocol

- **Status**: Approved
- **Date**: 2026-08-06
- **Authors**: TyProX Core Engineering Team

## Context
Keystroke telemetry payloads captured during typing runs are persisted to database tables and used for replay playback. As the platform evolves and new metrics (such as keypress pressure or touch coordinates) are added, payload schemas will inevitably evolve.

## Problem
Modifying telemetry array structure without explicit versioning breaks backward compatibility when replaying older test runs recorded under earlier schema versions.

## Decision
Every telemetry payload generated by the TyProX Telemetry Engine must specify an explicit integer schema version field:

```typescript
export interface VersionedTelemetryPayload {
  version: 1; // Explicit schema version identifier
  duration: number;
  mode: string;
  seed: string;
  telemetry: Array<{
    t: number; // relative time delta (ms)
    k: string; // key character
    y: number; // 0 = input, 1 = delete
    i: number; // target character index
  }>;
  attributes: {
    reactionTime: number;
    precision: number;
    consistency: number;
    rhythm: number;
    acceleration: number;
  };
}
```

We mandate forward-compatible serializers and parsers in `src/telemetry/serializers/`. If a future `version: 2` payload is introduced, `version: 1` parsers will continue to parse historical replays without corruption or failure.

## Alternatives Considered
1. **Unversioned Implicit Schemas**: Fragile; breaks when fields change.
2. **SemVer String Versioning (`"1.0.0"`)**: Unnecessary complexity for database JSONB telemetry payloads; integer versioning (`version: 1`) is simpler and faster to evaluate.

## Consequences
- **Positive**: Guarantees historical replay playback compatibility across all future platform upgrades.
- **Negative**: Serializers must maintain version migration handlers when schema updates occur.
